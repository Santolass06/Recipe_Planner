## Disciplina de verificação

- Toda a citação leva `file:line`. Toda a contagem (nº de testes, LOC, ocorrências) vem de output de comando colado no relatório, nunca afirmada de memória.
- Distinguir testes de comportamento de `export_bindings_*`. Comando:
  ```
  cargo test --workspace 2>&1 | grep '^test ' | grep -v '^test result' | grep -vc export_bindings
  ```
- Continuar o precedente de prova executável (testes que falham contra o código atual e passam a verde quando corrigido). **Validado na prática nesta ronda**: uma hipótese que parecia um achado ao ler o código (dedupe do backfill) foi refutada assim que virou teste executável — ver `audit/AUDIT-2026-08.md`, secção "Hipótese refutada".

## Onde vive o código desta auditoria — decisão revista

O plano original previa testes-prova em `crates/core/tests/audit_2026_08.rs`
(ficheiro de integração, fora de `db.rs` por completo). **Na prática, não deu**:
duas das funções mais relevantes para provar (`backfill_purchase_movements`)
são privadas ao módulo `db`, e um teste de integração externo só vê API `pub`
do crate. Tornar a função `pub` só para a testar seria mexer em código de
produção pelo motivo errado.

**Decisão tomada:** seguir exatamente o precedente já validado no próprio
repositório — `mod audit_2026_08`, acrescentado a seguir ao `mod audit_2026_07`
já existente no fim de `crates/core/src/db.rs` (mesma técnica, novo nome).
É aditivo (só linhas novas, zero edição a código existente) e consegue chamar
funções privadas por estar no mesmo módulo. Sinalizado ao utilizador para
poder redirecionar se preferir a via `tests/` externa (exigiria expor
`backfill_purchase_movements` como `pub(crate)` ou mais).

- Relatório: `audit/AUDIT-2026-08.md`.
- Este plano: `audit/plano-2026-08.md` (espelha o artefacto Traycer da sessão).
- Testes-prova: `crates/core/src/db.rs`, módulo `db::audit_2026_08` (aditivo).
